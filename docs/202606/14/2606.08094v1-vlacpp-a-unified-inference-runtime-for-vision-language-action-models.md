## 摘要
视觉-语言-动作（VLA）策略通常以 Python/PyTorch 堆栈形式提供，假定使用工作站级 GPU，这与机器人实际运行的硬件不匹配。我们提出了 vla.cpp，一个基于 llama.cpp 构建的可移植 C++ 推理运行时。据我们所知，它是第一个原生支持流匹配和扩散 VLA 推理模式的 ggml 类引擎，在该模式中，缓存的视觉-语言前缀由跨注意力动作专家消耗，并在多个求解器步骤上集成。同一个运行时通过一个请求/响应协议支持跨越五个主干和四个动作头家族的七种架构，每个模型都打包为自包含的捆绑包。在 LIBERO-Object 上，该引擎与最先进的检查点相差不到 200 个 episode 中的 1 个，并在 1.3 GiB 内存中以 100% 的成功率运行 BitVLA。相同的捆绑包在三个硬件层级上无需修改即可运行，从消费级 GPU 到 8 GB 嵌入式模块。跨硬件峰值性能分析表明，批量大小为 1 的 VLA 推理是计算受限的，因此利用率而非带宽是部署的关键；从该分析中得出的 IMMA 梯形 GEMM 将 BitVLA 每步延迟降低了 4.5 倍。然后，我们在 ALOHA 手臂上设计了一个机器人上压力测试，该测试隔离了学习型 VLA 必须在其训练的硬件上针对移动目标重新规划的延迟约束。代码、演示视频和可重复的基准测试框架可在 https://fai-modelopt-tech.github.io/vla-cpp.github.io/ 获取。

## Abstract
Vision-Language-Action (VLA) policies are typically shipped as Python/PyTorch stacks that assume a workstation-class GPU, a mismatch for the hardware on which robots actually run. We present vla.cpp, a portable C++ inference runtime built on llama.cpp. To our knowledge, it is the first ggml-class engine to natively serve the flow-matching and diffusion VLA inference pattern, in which a cached vision-language prefix is consumed by a cross-attending action expert integrated over several solver steps. A single runtime serves seven architectures spanning five backbone and four action-head families behind one request/response protocol, with each model packaged as a self-contained bundle. On LIBERO-Object, the engine matches a state-of-the-art checkpoint to within one episode out of 200, and runs BitVLA at 100% success in 1.3 GiB of memory. The same bundle runs unchanged across three hardware tiers, from a consumer GPU down to an 8 GB embedded module. A cross-hardware roofline analysis shows that batch-1 VLA inference is compute-bound, so utilization rather than bandwidth is the deployment lever; an IMMA ladder GEMM derived from this analysis cuts BitVLA per-step latency by 4.5x. We then frame an on-robot stress test on an ALOHA arm that isolates the latency constraint under which a learned VLA must replan against a moving target on the hardware it was trained for. Code, demo videos, and the reproducible benchmark scaffold are available at https://fai-modelopt-tech.github.io/vla-cpp.github.io/.

### 6. 论文的主要结论与发现

1. **统一便携运行时**：vla.cpp 是首个原生支持流匹配/扩散 VLA 推理的 ggml 类引擎，单二进制、单一捆绑格式服务七种架构，在模拟器和真实机器人上达到与 PyTorch 参考模型的行为保真度（BitVLA 和 π0 成功率匹配或接近）。
2. **计算受限而非带宽受限**：跨硬件 roofline 分析表明，单请求 VLA 推理中，视觉-语言前缀阶段（处理数百 token）是计算受限的，动作头阶段是内存受限的，因此部署的关键杠杆是算术单元利用率（而非带宽）和内存容量（而非延迟）。这区分了占用率（通过 IMMA 内核提升 4.5 倍）和容量（决定哪些模型能装入 8 GB 设备）。
3. **精度敏感性警示**：在模态编码器中使用降低精度（如半精度）时，位置嵌入索引的舍入差异会悄无声息地扭曲编码前缀，经流匹配求解器累积后导致实际动作偏移（最大达 1.97 单位），造成任务失败而无任何错误报告。必须进行数字一致性门控（fail-loud）。
4. **真实机器人延迟约束**：在 ALOHA 臂上，vla.cpp 将每块推理延迟从 ~620 ms 降至 ~470 ms，使观测更新鲜，成功率从 40% 提升至 87.5%，证实了降低延迟对闭环控制的直接益处。

### 7. 优点

- **创新性**：首次在便携 C++ 运行时中完整支持 VLA 特有的跨注意力缓存复用和流匹配/扩散动作头，填补了 llma.cpp 与 VLA 部署之间的空白。
- **统一性**：单运行时、单协议覆盖七种架构，包含首个在 ggml 类引擎中端到端运行三元 BitVLA 全部堆栈的实现。
- **工程贡献**：IMMA 张量核 GEMM 对三元权重的优化（4.5× 加速），以及静态图捕获（减少内核调度开销）带来的 7.95× 加速（SmolVLA vs. PyTorch eager）。
- **洞察深度**：通过 roofline 分析将 VLA 推理解耦为计算受限和内存受限两阶段，并指出利用率而非带宽才是关键杠杆，指导了内核优化方向；识别精度敏感性中的具体机制（离散索引舍入 vs. 连续插值），提供可操作的部署指导。
- **实验全面性**：覆盖模拟器多套件、多硬件层级、真实机器人应力测试，并提供统计学置信区间，确保结论可靠。

### 8. 不足与局限

- **缺乏动态权重分载**：对于大模型（如 GR00T-N1.6/N1.7），8 GB Jetson Orin Nano 统一内存仍不足，需将仿真器卸载到另一台机器，限制了资源受限设备的真正单机部署。
- **低比特量化支持有限**：仅原生支持 BitVLA 的三元配置，对其他低比特量化（如 4-bit、2-bit）未做优化，扩展性不足。
- **精度敏感性实验覆盖面有限**：仅详细分析了 SmolVLA（离散索引）和 GR00T-N1.6（连续插值），未验证其他架构（如 π0、Evo-1）是否也有类似脆弱性。
- **缺少与其他边缘推理引擎的直接对比**：虽然因技术原因无法公平比较，但若能与 LiteVLA-Edge、TensorRT Edge-LLM 在同一任务和硬件上做吞吐-延迟-成功率联合对比，将更具说服力。
- **重规划间隔研究基于单模型、单硬件**：SmolVLA 在 Orin Nano 上的结论可能不能直接推广到其他模型（如不同动作块长度、不同求解器步数的模型）。
- **依赖 Python 客户端进行控制逻辑**：服务器无状态设计虽灵活，但客户端仍依赖 Python 生态（如 lerobot），未实现完全纯 C++ 端到端控制。
- **未讨论训练阶段的影响**：论文仅关注推理，未涉及微调或量化感知训练等与部署的交互，但这是模型性能的关键维度。
